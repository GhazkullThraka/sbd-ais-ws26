### Are the missing readings in the table? 
The gateways insert batches of 15 readings at a time and due to the short between generating an ID and committing the transaction, the detector polled last_id, moved forward, and permanently skipped one of those batches.

### Why did the detector never see them?
The detector queries the database using SELECT ... WHERE id > last_id. Because it already saw higher IDs being immediately committed and updated its last_id, it permanently skips the lower IDs of the delayed transaction when they finally commit.

### Watch the detector's lines while the plant runs: what happens to delay, backlog and missing, and why?
delay and backlog grow continuously ntinously while the plant is active. The plant generates 600 readings per second, but since the model takes 3 ms to score a single reading, a single detector can process a maximum of about 333 readings/s. The detector cannot process data fast enough and falls further behind every second casuing the backlog to grow. By the time the detector finally processed reading seq=479 and found the first anomaly for M-029, the delay was nearly 60 seconds. Because the single polling loop takes 3 ms per reading, it can't keep up with 600 readings/s.

## Part B
### 1. Better Postgres Polling
With a 3ms delay, one detector processes 1000/3 = ~333 readings/s and the lab sends 600 readings/s so we need 2 instances. At production we need 301 instances for 100,000 readings/s

Scale: At 100,000 inserts per second, adding 301 detector instances simultaneously polling the database will cause severe locking and database exhaustion.

Complete and Ordered: Transaction commit delays cause polling mechanisms (tracking last_id) to permanently skip rows that commit out of order.

Fresh: At risk at scale, polling introduces artificial delays. And database index contention at high write volumes will push processing delays beyond 5 seconds.

Independent Consumers: Adding an archive and a dashboard requires additional polling queries, directly increasing the load on the primary Postgres instance.

### 2. Kafka
Scale: Kafka is built for high throughput and by creating a topic with 301 partitions, we can run 301 detector instances in parallel.

Complete and Ordered: By using the machine_id as the Kafka message key, all readings for a specific machine are routed to the same partition, guaranteeing sequential ordering for the model.

Fresh: No polling delays so consumers can continously recieve data in real time.

Independent Consumers: Consumer groups can independently track their own offsets and read the log entirely on their own without adding extra load to the broker. 

##
Overall, it would be better to implement Kafka for this pipeline. PostgreSQL is not viable for high-throughput streaming events; its ceiling likely around a few thousand readings per second before polling overhead locks become unmanageable. The gateways will write readings directly to Kafka, and the detectors will consume them via consumer groups. Postgres will probably be used as the system of record for the machine registry.
